# ScipionWeb — developer manual for AI agents

Read this before making changes here. Written for an AI coding agent, not end users — see `README.rst` for that.

For deeper, less-frequently-needed context, see:
- [`.ai/tech-debt.md`](.ai/tech-debt.md) — known problem areas
- [`.ai/roadmap.md`](.ai/roadmap.md) — planned/likely future work (draft, pending team review)
- [`.ai/protocol-form-compatibility.md`](.ai/protocol-form-compatibility.md) — how protocol forms must mirror Scipion's form semantics (path params, conditions, expert level); read before touching `ProtocolForm`

## What this repo is

The new React-based frontend for Scipion, replacing both the legacy Tkinter desktop GUI and an intermediate NiceGUI attempt (the README only mentions NiceGUI — both are accurate, NiceGUI was a stepping stone that didn't ship). Talks to `ScipionAPI` purely over HTTP — the one genuinely isolated repo in the 5-repo ecosystem (no direct Python imports of `pyworkflow`/`pwem`/etc.).

## Stack

React 18 + TypeScript + Vite, TailwindCSS v4 + ShadCN/UI, ReactFlow (protocol workflow graphs), Axios, React Query. The app was originally built on the TailAdmin dashboard template, so some template leftovers remain — e.g. `src/components/ecommerce/` is not imported anywhere (and is the only user of `@react-jvectormap`). Don't treat template code as part of the Scipion app.

## Architecture map

- `src/api/` — HTTP calls to ScipionAPI (`auth.ts`, `projects.ts`, `protocols.ts`, `plugins.ts`, `settings.ts`, `users.ts`).
- `src/services/ProjectService.ts` + `src/ProjectServiceContext.tsx` — the main data-fetching/state layer for project data. HTTP API modules use `BASE_URL = "/api"` from `src/config.ts`; the tracked `.env` value alone does not establish the effective API URL.
- `src/adapters/`, `src/stores/` — data shaping and state management.
- `src/components/`, `src/pages/`, `src/layout/` — UI. Project workflow state lives in `src/pages/Dashboard/projects/ProjectPage.tsx`; the home dashboard lives in `src/pages/Dashboard/homepage/Home.tsx`.
- `src/components/protocol/` — forms, protocol actions, outputs, logs, and wizard dialogs. `src/utils/protocolform.*` implements shared form semantics.
  Form wizards run the plugin's own code on the server (`POST /projects/{id}/wizards/run`, `use_wizard_runtime`); the dialogs it opens come back described (`src/utils/protocol_wizard_runtime.ts`) and `WizardRuntimeDialog` renders each kind generically (confirm, choice, form, list, preview with images/sliders/rings, file, 3D point). There is no per-wizard UI.
- Protocol tags: `src/hooks/useProjectTags.ts` holds the one copy per project (tag list + `protocolId -> tagIds`, seeded from each graph load); graph cards read it through `ProjectTagsContext`, the table through props, and every assignment goes through its serialized per-protocol `writeProtocolTags`. Unknown ids are hidden, never dropped. Helpers in `src/utils/protocol_tags.ts`; one `TagsSubmenu` for card dropdown, card context menu and table.
- `src/components/analyze/` — metadata, CTF, volume, coordinate, and tomography viewers. Changes to request cancellation and caching must preserve isolation between viewer requests. `analyze-output-dialog.tsx` shows the protocol ID as a circular badge, with the protocol status hue, before its label in both floating and external windows. Callers pass the live status when known; other entry points read it once per opening through the project service, rejecting mismatched protocol IDs and late responses. Unknown status stays neutral; `ExternalWindowPortal.subtitle` accepts React content for this shared subtitle.
- `src/components/analyze/image-preview-dialog.tsx` — shared image detail window used by metadata and CTF previews (zoom, pan, rotation, brightness/contrast, external window). Callers provide an image loader; the dialog owns cancellation and object URL cleanup independently of thumbnail requests.
- `src/components/monitor/` — the streaming monitor. The project toolbar opens it in a floating window (`StreamingMonitorWindow`) that can move to a browser window of its own and back, like the viewers: the monitor stays mounted in one content host, so it keeps its points. It is also a page at `/project/:projectId/monitor` (and a route of the project page widget). The monitor asks its own document whether it is seen, so it keeps polling in another window; its dialogs go to that window's body. It polls `GET /projects/{id}/monitor` while its window is visible, every 15 s by default; the header chooses 5 s to 1 min or paused, kept per browser in `localStorage["scipionweb.monitor.pollSeconds"]` and keeps the CTF points between polls: it sends back the `lastRowId` cursor (the order rows were written in, which parallel steps make differ from micrograph ids) and adds the new points, kept in micrograph order (`mergeSeries`; a `reset` or another `setId` starts again, and `more` is read at once). The server marks the thresholds each point goes past; the page groups consecutive micrographs past the same threshold into one alert (`alertEpisodes`, failed estimations are skipped). Saving the thresholds reads the series again. Plots are Plotly `scattergl` with `APP_TOKENS` colours; a point opens its micrograph in `ImagePreviewDialog`. Below them: the latest 20 micrographs (`LatestMicrographsTable`, each image read once per micrograph), and histograms of the CTF resolution and the defocus coverage, with the last 50 micrographs drawn over the session from 100 on. Coordinates per micrograph come apart from the CTF points (`picking`, merged with `mergePicking` and its own cursor) because picking comes later; `withParticles` puts them on the points and works out the `minParticles` alert on the page. The header chooses the CTF output and, with several, the picking (`coordinatesSetId`) and the 2D classes (`classesSetId`, which brings its own picking) to follow; changing any reads everything again. With a streaming 2D classification reading the particles, `ClassesGallery` shows the class averages biggest first, through the metadata image route (`objects` table, `stack` column, `contrastMode: "enhanced"`) with the classes' `version`: the classifier rewrites its averages in place, so a new round is a new image and an unchanged one is not read again. The header bell also gets the monitor alerts of streaming projects (`status: "alert"`, from `/workspace/protocol-activity`); one opens its project with `?monitor=1`, which `ProjectPage` turns into the open monitor window.
- The monitor header’s `CustomizeMonitorView` popover, beside the refresh interval selector and Thresholds button, shows/hides individual plots and sections immediately, with separate single particle and tomography choices. `monitor-view-preferences.ts` stores choices per JWT subject in this browser (`scipionweb.monitor.sections.v1:<subject>`), with all sections shown by default and a restore action. Hiding sections does not stop the monitor polling or its alerts; the tomography output selector stays accessible even with its pipeline hidden. The popover uses the trigger’s document body in external windows. Output selectors have visible labels above them (CTF, Picking, 2D classes and Tilt series).
- The monitor header shows session status with Refresh and the alert bell beneath Updated, then time/refresh controls on the left and Customize view/Thresholds on the right, then available output selectors side by side below a horizontal separator, followed by `QualitySummary`, pipeline and detailed plots. `quality-summary-data.ts` assesses a configurable window (default 100 imported movies for SPA, falling back to micrographs when movie lineage is unavailable, or 20 tilt series). `GET /monitor?qualityWindowSize=N` returns a bounded fresh `exposures` snapshot for both comparison windows: movie import row order, explicit aligned/CTF availability and associated measurements from the selected chain. It updates late results independently of incremental plot cursors; missing movie results are labelled No evaluation available: their absence cannot establish that they are pending or discarded. Legacy API responses and micrograph-only imports retain the micrograph summary. Tilt-series and micrograph fallback windows use item-id order against current thresholds, including slider edits immediately. Within limits requires all enabled measurements; failed CTF estimates, incomplete tilt series and missing values are separate states and never count as within limits. Quality percentages use only valid within/outside threshold decisions; assessment coverage uses those decisions divided by the whole recent window. CTF failures, unavailable results and incomplete measurements stay separate; metric-specific reasons use measured items and can overlap. Trends compare disjoint full windows only when both have full evaluation coverage and complete measurements. Movie dose and 2D classes are separate from this per-item summary. The summary can be hidden in Customize view. Its metric cards, pass rate and comparison include only visible metrics; hiding a metric never changes project thresholds or alert generation. In tomography, CTF resolution, astigmatism and failed-CTF tilt checks follow the tilt-series table visibility; angular coverage has its own Customize view option shared by both summaries, while defocus, tilts kept and alignment residual follow their own plots. Its window size is edited in the Thresholds dialog, separately for SPA and tomography. `quality-window-preferences.ts` validates whole numbers from 1 to 5000 and persists them per account in this browser (`scipionweb.monitor.qualityWindow.v1:<subject>`); these display preferences never enter the server’s thresholds PUT. Saving only the window size does not write project thresholds. Movie windows request a resized snapshot without discarding the cached plots.
- `MonitorTimeRangeSelector` offers Entire session, Last 30 min and Last 2 h, with presets remembered per account and SPA/tomography view. `monitor-time-range.ts` shares X zoom/pan and reset between session plots, filters histogram/table records, ignores Y-only relayout and programmatic range echoes, and gives Plotly every time in local wall time with no zone (`plotlyTime`, `plotlyPointTime`), reading its zooms back the same way (`fromPlotlyTime`): Plotly reads a date string from its year to its seconds and drops any zone, so points sent with their offset (`+01:00`, as the API sends them) and a range sent in UTC were hours apart and no point was drawn while a stream ran. Live windows end at the server snapshot time; completed-session windows end at the newest recorded item and retain stable item-order axes. Custom zoom is project-local; full caches, alert generation, the count-based Recent quality window, pipeline totals and current 2D class snapshots remain intact. Timestamps represent Scipion records, not microscope acquisition times; unknown times are excluded only in timed views.
- Monitor plots with thresholds show `ThresholdSliders` above the plot. Changes update threshold lines, point colours and the threshold form immediately while polling continues; they save automatically after 400 ms without movement, with serialized writes and a reload of both views. The thresholds endpoint is a replacement PUT: every write merges the edited fields into the latest complete snapshot at queue execution time, preserving the other endpoint and both views’ limits. Failed saves keep the edited values and show an error. Defocus uses one slider with two thumbs for its minimum and maximum, which cannot cross. Slider scales stay fixed across autosaves and polling; they expand only when an external value exceeds the current scale. Disabled limits can be enabled or switched off. Plots without a corresponding threshold have no slider.
- Acquisitions (both views): with several imports in the project, `AcquisitionSelect` (`monitor-parts.tsx`, shown only then, open ones marked with ●) chooses the branch followed (`acquisitionSetId`; null lets the server follow the open one that received something last, so a new import is followed from its first item). Choosing one forgets the CTF, picking, classes or tilt series chosen, which belong to the other branch, and reads everything again.
- Stream flow (both views; tomography with its own thresholds `maxTiltPauseMinutes` and `maxTiltSeriesStallMinutes`, and the pause told in tilts, `activityUnit`): the answer's `flow` (read by `monitorFlow` in `api/projects.ts`) is shown above the pipeline cards by `StreamFlowStatus` (`monitor-parts.tsx`): a pause of the acquisition (no new movies for `maxMoviePauseMinutes` while the import is open, with how long the import still waits), an import that stopped without closing its Set, a finished acquisition (the import closed its Set: never told as a pause) or a complete session, and each stage with items waiting that gave nothing for `maxStageStallMinutes` (also marked on its card, `stalledMinutes`). Both thresholds are in the Thresholds dialog, in minutes. The bell gets the same conditions from the server.
- The plot cards of the quality and session sections can be put in another order (`SortableCards`): dragged by their handle only (dragging over a plot zooms or selects a time range) or moved with the arrow keys from it. `monitor-card-order.ts` keeps the order per account and view in this browser (`scipionweb.monitor.cardOrder.v1:<subject>`); hidden cards keep their place, and Restore default view in Customize view restores it.
- Tomography view of the monitor (`TomoMonitorView`): shown when the streaming answer says `tomography` (tilt series in the project), alone or as a tab next to the single particle view. It polls `GET /projects/{id}/monitor/tomo` (one row per tilt series, the whole list each time), opens a tilt series with `.../monitor/tomo/tiltseries?tsId=` (its tilts by angle) and draws tomograms with `.../monitor/tomo/tomograms/{setId}/{itemId}/slice` (central slice). Its thresholds are `TOMO_THRESHOLD_ORDER` (the CTF ones are shared with the single particle view). Shared pieces live in `monitor-parts.tsx` (the stage card shows each backlog's estimated time, `formatEta`, or that it is stalled). When nothing streams (`streaming: false`) both views are a quality overview: the title says so, rates and backlogs are hidden, and plots put the micrographs or tilt series in their order instead of processing time (which would bunch them together).
- `TomographySummary` adds a selected-range overview before the tomography pipeline, independently hideable in Customize view. `tomo-overview-data.ts` counts complete/incomplete series, completed series outside visible enabled limits, explicitly disabled present tilts (`tilts - enabledTilts`, only for consistent known counts), and enabled-tilt angular coverage of complete series. Incomplete series never fail the angular/count target prematurely; missing angles/counts stay unknown. Angular coverage has its own visibility option and requires both negative and positive targets; disabling the target shows median angular span. The latest series short of the target opens its existing detail. Operational counts refer to the selected tilt-series output, not inferred upstream/downstream discards or their causes.
- `src/hooks/useProtocolLogs.ts` + `ProtocolLogsPanel.tsx` — log windows, history loading, global search, and full log copy.
- `ProtocolSummaryPanel.tsx` — the protocol's summary as the desktop Summary tab (`fetchProtocolSummary`): Scipion's markup (`parseSummaryLine`: `*bold*`, `_italic_`, `'''fixed'''`, URLs, `[[path][label]]`), and `[[sci-open:ID][name]]` opening that output in `AnalyzeOutputDialog`. `buildSummaryBlocks` lays it out: `label: value` and `label = value` lines become a fact list, and the comments, error and warnings get boxes of their own. It reads again when the protocol's status changes, and every `SUMMARY_POLL_MS` (10 s; one read costs about 2 s, a child process) while the protocol is running, launched or scheduled and the page is visible; a finished one is read once. Shown as the form's Summary tab (between Outputs and Logs; the form's tabs have fixed values, `SUMMARY_TAB`) and as a tab of the workflow's bottom panel (`WorkflowLogsDock`: Summary | Logs, the logs read only on their tab).
- `src/hooks/`, `src/lib/`, `src/utils/`, `src/context/` — supporting code.
- Multiple Vite build targets, not just one app: `build:web` (the full app) and `build:widget:{list,page,protocoldetail}` (standalone embeddable widgets, each with its own `vite.project*.config.ts`) — check which mode you're actually building/testing against before assuming "the app" means the whole thing.

## Testing

- CI already exists: `.github/workflows/tests.yml` (Node 20.18.0, `npm ci && npm test`).
- **Run tests with `npm test`, which uses Vitest** (`vitest --config vitest.config.ts run`) — not Jest.
- Vitest uses `jsdom`, the `@` alias for `src`, and `src/test/setup.ts`. Tests live in `src/components/tests/`, alongside some source files, and in `src/test/`.
- For a focused regression, use `npm test -- <test-file>`; run `npm run build:web` when validating the app build, or the appropriate widget script for widget changes.
- `engines.node` is strictly pinned to `>=20.18.0 <21` (matches `.nvmrc`) — don't assume a newer/older Node works.

## Behavior to preserve

- ReactFlow node IDs are the canonical protocol identity; reject protocol detail responses that belong to another protocol.
- Output refreshes must preserve the displayed order by output name across graph, table and form updates. Append new outputs and remove absent ones; the output panel selection follows the output name, scoped to its project and protocol, rather than its array index.
- With output thumbnails enabled, graph nodes display scalar outputs as compact name/value rows, retaining drag-and-drop input behavior. With thumbnails disabled, scalars retain the standard output pills. Scalars do not consume thumbnail columns; mixed output layouts preserve the protocol's output order.
- Container resizing and routine graph refreshes (including those triggered by closing protocol forms) must preserve viewport pan and zoom in Grid and hierarchical views. Automatic centering is reserved for initial load and explicit layout/navigation actions.
- Restart/status refreshes must preserve correct elapsed sessions; retain the regression coverage in `src/components/tests/projects/` when changing workflow state.
- Home opens the last accessed project when available (`scipion.home.lastOpenedProjectId.v1` in localStorage), rather than choosing solely by update time.
- Log search and full copy must operate on the complete log through the service API, not just the currently loaded window.
- UI text and code comments use English.

## Actions of a running protocol

- Both menus of a protocol card (the dropdown and the right-click one) list, under Stop, what a running protocol offers (`ProtocolRunActions.tsx`): STOP STREAMING, APPROVE CHECKPOINT… They are read when a menu opens, never on page load (each read starts a short process on the server), and only for a running protocol. Choosing one asks for confirmation (each says what it does; neither can be undone) and posts it. Stop still aborts the protocol: Stop streaming lets a streaming import close its output and finish, and the protocols after it finish in turn.

## CTF viewer (SetOfCTF)

- `ctf-viewer.tsx` gets every CTF of the Set (its plots and statistics use them all) but its table draws only the rows on screen (fixed `CTF_ROW_HEIGHT`, spacer rows above and below): a CTF picked in a plot scrolls the table to its index, as its row may not be drawn. The plots of every CTF are `scattergl`; the selected one stays SVG, drawn above. Its micrograph and PSD are fetched with `cache: "default"` (the server ETags them), and those of the next row are asked for a moment later, so going down the table shows each one at once.

## Selections in the metadata viewer

- **By ids:** rows clicked one by one, or a frozen selection. These ids are already known.
- **By index:** Select all, shift ranges, criteria. The viewer keeps `{baseMode: "none" | "all", ranges}` over the rows in the current sort.
- **Index into ids:** Create subset (`resolveSelectedRowIds`) and Freeze selection (`materializeIndexSelectionToIds`) ask the API for the ids in one request (`resolveMetadataSelectionIds`, `POST …/selection-ids`, with the sort).
- **Older APIs:** only when the service has no such method, or the API answers 404/405, does the viewer still read the table page by page.

## Class images in the metadata viewer

The root `objects` table of a SetOfClasses2D/3D is requested with `contrastMode=enhanced`; its representatives (`N@stack.mrcs`, or a volume file) are then drawn from their original data (`app/backend/utils/class_average_display.py`, read with pwem's pure-Python readers: a broken file raises instead of crashing the process), never from the renderer's 8-bit image. 2D averages are scaled to the noise of their background ring (inside any mask the plugin applied), so every class shows the same background gray, then lightly smoothed and enlarged with Lanczos. 3D classes show as a lit surface (largest connected body of the densest voxels, volume binned to 128), a projection or the central slice (`volumeView`). Display only: nothing stored changes. The image cache key (and so the browser ETag) includes `CLASS_DISPLAY_VERSION`: bump it when the drawing changes.

## Themes (light, dark, system)

- `context/ThemeContext.tsx` holds the preference (`light`, `dark` or `system`, in `localStorage["theme"]`; `system` follows `prefers-color-scheme` live) and puts the `dark` class on `<html>`, `<body>`, `#root` and the widget roots. `index.html` applies it before the first paint. Settings → Appearance saves the user's theme and applies it. `useIsDark()` answers also outside the provider (widget build). It cleans each new stylesheet of `prefers-color-scheme: dark` rules once (only `<head>` is watched).
- One source of colour: `styles/theme-tokens.css` (`--app-*` for light and dark). `theme/tokens.ts` mirrors the values for the MUI theme and canvases (`theme.test.tsx` keeps them equal). Tailwind has them as `bg-app-surface`, `text-app-muted`, `border-app-border`, `text-app-success|warning|danger`… (`@theme inline` in `index.css`). `theme/muiTheme.ts` (`createAppTheme`) is the global MUI theme (`AppMuiThemeProvider` in `main.tsx` and the project page widget); components that need their own (portals of external windows) extend it: `createAppTheme(mode, options)`.
- Colours in `sx`, inline styles and CSS modules use the variables, not hex values: the neutral scale `--app-n-0` (white) … `--app-n-900` keeps the light values and is inverted in dark; `--app-<hue>-50|100|200` are tint backgrounds and `--app-<hue>-700|800|900` their text (red, amber, yellow, green, emerald, blue, indigo, sky). Light text on dark overlays and dark overlay backgrounds stay literal on purpose. Canvas and three.js code cannot read CSS variables: use `APP_TOKENS`/`NEUTRALS` from `theme/tokens.ts`. Scientific images and colour maps keep their own colours.
- Protocol node cards keep their status hue in dark (a deep tint and a vivid border, `ProtocolNodeCard.module.css`).

## Runs per user

- A launched protocol waiting for one of its user's run slots (Settings → Instance → Max concurrent runs per user; 0 = no limit, the default) gets `waitingForSlot` `{inUse, limit}` from the API, in the graph and in the active-protocols poll (`ProjectPage` merges it into nodes and rows).
- `ProtocolNodeCard`'s status badge then reads "launched · waiting for a run slot", with `runSlotWaitText` as its tooltip. The Settings field accepts 0–64 and explains that runs launched together count as one, and streaming runs still receiving data never count.

## Permissions

- The API decides what a user may do (roles of permissions, groups, project access levels: see ScipionAPI's AGENTS.md). The web only hides what would be refused: `usePermissions().can("plugins.manage")` reads the signed-in user's `permissions` from `/auth/me`, once per session (`loadCurrentUserOnce`, forgotten at login and logout).
- Settings shows each tab to whoever may use it: Instance, Host and Environment (`settings.manage`), Jobs (`jobs.manage`), Users (`users.manage`), Roles (`roles.manage`), Groups (`groups.manage`), Audit (`audit.view`), Usage (`storage.view`). Panels with their own actions (Jobs, Users, Roles, Groups, Audit, Usage, Tags) get none in the header. The plugin pages hide installing, updating and removing without `plugins.manage`.
- Sharing a project picks an access level (view, work, manage) and users or groups (`ShareProjectModal`, `/access/groups/names`).
- A project the user only views (`project.access === "view"`, from `GET /projects/{id}`) is read only in `ProjectPage`: its menus hide the items that change it (`READ_ONLY_HIDDEN_MENU_ITEMS`, merged into the menu visibility policy; run actions such as Stop streaming follow Stop), the actions they and the shortcuts call refuse with a toast (`refuseWhenReadOnly`), the canvas menu has no Add protocol, protocol forms open with `readOnly` (no Save nor Launch) and the header shows a View only badge.
- Administrators (`users.manage`) see new sign-ups waiting for activation in the activity bell (`status: "account"`); the event opens `/settings?tab=users`, as Settings opens the tab named in `?tab=` when the user may see it.
- In the file browser, a user limited to the project and the data folders (`SCIPIONWEB_DATA_ROOTS`) gets each data folder as a shortcut chip (`dataRoots` of `start-path`; none when the data folder is the whole server).
- Groups choose what their PIs may do in their members' projects (PI access: None, View, Work, Manage). Project cards and rows label how the user reaches a project from the API's `accessVia` (`utils/project-access.ts`): Owner, Shared · level, Group · level (a PI), All projects · level (a role).
- Settings → Audit (`audit.view`, `AuditPanel`) reads the audit log newest first, by kind and search, with Older events for the next page.
- Settings → Usage (`storage.view`, `UsagePanel`) has two parts, Disk and Computing.
- Its Disk part (`DiskUsagePanel`, `api/storage.ts`) shows what the projects take on the disk, as the API's background measurer last measured it:
  - the free space of the projects' disk;
  - tables by user, by group and by project, sorted by size;
  - clicking a user shows their projects;
  - projects untouched for 90 days are marked as unused;
  - Measure all again, or measure one project again;
  - the panel looks again every 15 s while measures are pending.
- Its Computing part (`ComputeUsagePanel`, `api/usage.ts`) shows what the runs took in a period (this week, this month, last month, last 30 days, this year, or a custom range):
  - GPU hours, GPU use (how busy the GPUs given were, over the GPU hours measured; "—" when none was), run hours, runs and failed runs;
  - a GPU use column in each table, and "N % busy · memory" under each measured run's GPU hours;
  - tables by user, by group, by protocol and by machine (with GPU hours per GPU), sorted by GPU hours;
  - clicking a user lists their runs;
  - the runs running now;
  - Export CSV of the table shown.
- The Projects page shows no usage lines (the user found them noisy): only a warning for a quota from 80 % (amber) or full (red, "nothing new can be launched").
- Settings dialogs and confirmations use `pages/Settings/SettingsDialog.tsx` (the web's dark header, rounded buttons, red gradient for what destroys or interrupts), never `window.confirm`.

## Facility mode (branch `lims`, in progress)

Off by default, set per installation (API `SCIPIONWEB_FACILITY_MODE`). `hooks/useFacilityStatus` reads `GET /facility/status` once per session (`api/facility.loadFacilityStatusOnce`; a change of the mode shows after a reload) and gives `facilityCan(permission)`, false for everything when the mode is off. The facility is one menu entry, "Facility" (after Workflows), leading to `/facility/<tab>` (`pages/Facility/FacilityPage.tsx`): a tab per part, in the order of `layout/facilityNav.FACILITY_TABS`, each shown to whom holds one of its permissions; `/facility` or a tab the user may not open goes to their first one. The entry is absent when the user has no tab, so without facility mode the menu is the one it always was. Today: Samples & grids (`SamplesPanel`, any facility permission sees them, `facility.sessions` or `facility.manage` edits them; a sample with its boxes, each box's grids shown as position slots coloured by status; the dialog edits the whole tree, a new box starting with four grid rows and blank rows left out; samples, boxes and grids keep images through `pages/Facility/ImageStrip` — thumbnails that open bigger, added several at once and removed from the bigger view, kept at once, only for rows already saved; object URLs of images are kept for the session in `api/facility.fetchFacilityImageUrl`, as an image never changes), and Microscopes (`MicroscopesPanel`, `facility.manage`, each with its detectors — a `DetectorEditor` per camera in the dialog: name, the name in the movies' metadata, behind the energy filter, gain with flip/rotation, its calibrated pixel size per magnification; ids kept, so a save sends the whole list and the API deletes the ones left out; a new microscope starts with one detector, dropped if left empty — and a photo, read with the session as an object URL versioned by `photoUpdatedAt`; the dialog uploads or removes it on Save); the calendar, the monitor, reports and templates come as tabs. Pages built like Settings share its look through `pages/Settings/useSettingsStyles(isDark, fontSizes)`. The facility pages read bigger than Settings (the user's preference for new screens: fields ~15.5 px, notes and buttons ≥13.5 px, no 12 px text): they take their styles from `pages/Facility/facilityStyles.useFacilityStyles()` and their other text sizes from `FACILITY_TEXT`. A sidebar entry stays lit on the pages under its path (`/facility/…`, `/plugins/<name>`). "My sessions" (`MySessionsPanel`, tab `mine`, `permissions: []` = every user while facility mode is on, so a user without facility permissions sees the Facility entry with only this tab) shows `GET /facility/my-sessions`: each session read only (status, microscope, day, the user's name only to a PI, group, booking), until when its raw and processed data are kept, "From the facility" (its `userNotes`), each DATA with its grid, `DatasetProgress` and its project and monitor; the facility's download instructions; and the samples. It reloads every 30 s while a session acquires. The session dialog has "Notes for the user" beside the staff notes, and Configuration a "For the users" card (retention days and download instructions). The session dialog has the session's CTF limits (minimum and maximum defocus, resolution; a new session starts with the facility's, from `getFacilitySettings`; empty keeps the template's), only for SPA: a tomography session sends none. Configuration's "Policies" card sets the owner of a DATA's project and what its user and group may do in it, the calibration tolerance, the stalled minutes, the watcher's seconds and the CTF limits a new session starts with. Each DATA of a tomography session shows its navigation report (`pages/Facility/NavigationReport.tsx`, tomo5-mapper on the API): "Navigation report" opens it in a new tab (the tab opens on the click, then gets an object URL of the HTML: `fetchNavigationReportUrl`), "Making…" polls every 15 s, and the staff (the Sessions list, where `onProcess` is given) make it or try again; My sessions shows it once done. The Calendar tab (`pages/Facility/CalendarPanel.tsx`, `permissions: []`: every user while facility mode is on) books the facility's resources: a FullCalendar (week by default, month and day; weeks start on Monday; times in the browser's zone) with a chip per resource to show only some (kept in localStorage `scipionweb.facility.calendarResources`), dragging over a time opens the booking dialog (whole days picked in the month start and end at the resource's `dayStart`). The staff (`isStaff`: facility.sessions or facility.manage) see a "Requests waiting" card ordered by priority then age, with Confirm / Other time / Reject (`DecisionDialog`, reason and priority), book for anyone or block (kind downtime/maintenance/special), and change or cancel any booking from its details; a user asks for time ("Ask for time": resource, technique for a microscope, from/to as datetime-local sent as ISO, with a line "Read as …" saying the dates read, since the inputs follow the browser's order; a start already gone is said there and disables Ask for a user, one of their groups, what it is for), sees "My bookings" (always, with a line saying where requests wait when there is none; the staff only when they have some) with "Take it"/"Decline" for another time offered, and of the others' bookings only "Booked". Requests show hollow, confirmed filled with the resource's colour (`ResourcesDialog.resourceColor`), blocks grey. Managers open "Resources" (`ResourcesDialog`): name, microscope, colour, how it is charged, shortest and longest booking, when its day starts, in use, needs training. Policies has the facility's time zone. The room screen (`pages/Facility/RoomScreen.tsx`, route `/room?token=…` among the public routes of `App.tsx`, outside the app layout and with no signed-in user) is a dark full-screen page for a TV beside the microscopes: clock, a tile per microscope (photo through `roomMicroscopePhotoUrl`, its state as a big coloured badge, its session with its people, grids, progress and alerts) and the next sessions, from `api/facility.getRoomView` (plain fetch with the token; reloads every 30 s, "reconnecting…" while the API does not answer, a message when the link no longer works). Over every page, below the header (`layout/AppLayout`), `components/facility/FacilityAlertsBanner` shows the facility's open alerts to its staff, reloaded every 30 s: red and large while nobody is on one, with "I'm on it" for those who run sessions; once all are taken, a thin amber line folded to its count, unfolded on demand (with who); it goes away when the watcher resolves them (there is no dismissing: an alert goes when its cause does). A Configuration tab (`ConfigurationPanel`, `facility.manage`; its sections are tabs of their own — Naming, Policies, For the users, Alerts, Room screen — all kept mounted and only hidden, so what is typed in one survives looking at another, the last one remembered in localStorage `scipionweb.facility.configurationSection`) sets the session name pattern with a live example (`useConventionsPreview`, which asks `POST /facility/settings/preview` as one types), the pieces it takes, the presets (CNB-CSIC) and the neutral default; its "Alerts" card sets who is mailed the alerts (`alertRecipients`; empty: the users who run sessions, as each chose; the mail server itself is in Settings → Notifications), and its "Room screen" card makes, copies, opens, renews (the old link stops) or turns off the link of the room screen; the microscope dialog sets its code, grids in the autoloader and DATA/ATLAS folder patterns with the same live example. The session dialog offers the microscope's positions (1 to its `gridSlots`) and shows each saved DATA's folder. The first tab is Sessions (`pages/Facility/SessionsPanel.tsx`, any facility staff; editing for `facility.sessions`/`facility.manage`): the list (planned and acquiring by default, a filter for the rest, a search) shows each session with its folders for the microscope (`SessionFolders`: a copy button per folder and "Copy all"; copying falls back to `execCommand` because the microscope PCs open the web over plain http), Start/Finish buttons that send the session back with its new status (`api/facility.sessionPayloadOf`), and Delete only while planned. The dialog: microscope (only those with sessions; a new session takes the only one that runs them), technique, status, user, group, day, EMhub booking, the name (empty: the server names it; disabled once acquiring), and a row per DATA with its grid (an Autocomplete over every sample's grids, grouped by sample) and detector ("From the movies" by default); images of the session, the ATLAS and each saved DATA are kept at once like the samples'. Each DATA of the folders shows, on a line of its own under the folder (so it is not cut), where its acquisition is (`DatasetProgress`: the API's `watch` as a badge, and `describeAcquisition`: movies, size, pixel and whether calibrated, magnification, dose on the sample or else at the camera, frames, last movie; the tooltip lists the camera name, EPU's nominal pixel, the reader's warnings). While a session acquires and no dialog is open, the list reloads quietly every 30 s. The dialog chooses the processing template (`fetchWorkflows`, the Workflows page's list; one that cannot load is disabled with its reason) , "Launch it by itself" (`autoProcess`) and "All grids in one project" (`oneProject`: every DATA a branch of the session's project); each DATA shows its processing (`DatasetProcessing`: queued, making its project, processing, failed with the message in the tooltip, "Project deleted" when it was launched but its project is gone), "Project" and "Monitor" buttons (`DatasetProjectLinks`, shared with My sessions: `/project/load/<id>`, `/project/<id>/monitor`), and "Process now"/"Try again" (`processSessionDataset`) for the staff while it has no project. ## Known gotchas

- Vitest is the only test runner (Jest was removed). `@testing-library/jest-dom` is still a dependency on purpose — it provides DOM matchers for Vitest, not Jest itself.
- External windows (`ExternalWindowPortal`) share the page's JavaScript thread and copy its stylesheets. The copy is incremental (`mirrorDocumentStyles`): a sheet is turned into text again only when its element changed (`markMirroredStylesDirty`, from the `<head>` observer); one that grew at its end (emotion's `insertRule`) gets only its new rules. Re-reading every rule on each `<head>` change made the whole application slow while a popup was open, so keep syncs cheap.
- This repo is standalone/HTTP-only towards Scipion — if something looks like it needs a direct Python/Scipion import, that's a sign it belongs in `ScipionAPI` instead, not here.

## Notifications

Settings has a "Notifications" tab for every user (`pages/Settings/NotificationsPanel.tsx`, `api/notifications.ts`; it takes the bigger facility sizes through `useFacilityStyles`): "My notices", each kind with how it reaches the user (by mail at once, in one mail a day, only in the web, not at all; "Default: …" goes back to the default; mandatory kinds say "always mailed" and offer only mail), saved at each change. Whoever holds `settings.manage` also turns the mail on ("Send notices by mail", off by default: no mail at all until then), sets the mail server (moved from the facility's Configuration: password typed only to change it; the web's public address for the links of the mails; the daily mail's hour and time zone; a test mail to an address), the defaults for everyone, and sees the latest mails sent with their state and error. The header's bell (`components/header/ProtocolActivityBell`) shows the user's notices (status `notice` from the activity endpoint; `link` is the page to open, `/settings?tab=notifications` without one): opening the bell marks them read (`markNotificationsRead()`), opening one marks it. Mails link to `/settings?tab=notifications` to change one's choices.

## The menu shows only what the user may open

`layout/AppSidebar` filters `navItems` by their `permissions` (any of them; none = everyone) with `usePermissions`, waiting for them before showing a guarded entry: Workflows needs `projects.create`, Plugins `plugins.manage` or `projects.create`; Home, Projects, User profile and Settings are for everyone. Facility goes after Workflows, or after Projects when Workflows is not shown. The API refuses what the menu hides anyway.

## Deleting an account

Settings → Users has a delete button per account (not one's own): `DeleteUserDialog` reads `previewUserDeletion` and lists the projects that go with it (size, shared with how many, running), warns when some are shared, says what stays in the facility, shows the blockers, and enables "Delete the account" only once the account's address is typed (`deleteAdminUser`). Projects that could not go are told in a toast; deleting again retries.

## A forgotten password

Sign in's "Forgot password?" (shown only when `api/auth.passwordResetAvailable`: the mail is on and the web's address set) opens `/forgot-password` (`pages/AuthPages/ForgotPassword.tsx`: the address, then the API's same answer whatever it is), and the mailed link opens `/reset-password?token=…` (`ResetPassword.tsx`: the new password twice; a used or expired link offers a new one). Both are public routes in `App.tsx`; `api/auth.forgotPassword`/`resetPassword` call the API without a session.

## An error stays in its part

`components/common/PageErrorBoundary` keeps a render error inside a part of the web: around each page's `<Outlet/>` in `layout/AppLayout` (reset when the address changes, so another page starts clean), around the whole `<Routes>` in `App.tsx` (the public pages), and silent (shows nothing) around the menu and the facility alerts banner. The message says what failed, with Try again, Reload the page and Go to Home; a chunk no longer on the server (the web updated while open) asks to reload instead.

## A workflow's requirements

`components/workflows/WorkflowRequirements` shows, in the Workflows page's details and in the import-from-file dialog, the plugins a workflow misses with "Install missing plugins" (`installPluginsBatch` with the pip names the API resolved; a plugin with no known package is listed apart, to look for in Plugins, never installed blindly; for `plugins.manage`; others are told to ask an administrator; the list reloads after), the protocols this installation does not know when the workflow does not say its plugins, and the warning to migrate such a workflow. Broken workflows never reach the web (the API hides them).

## Disk quotas

Settings → Usage → Disk ends with `pages/Settings/StorageQuotasCard`: each quota with a bar (amber from 80 %, red when full) and, for `settings.manage`, its limit in GB to save or remove, and a row to add one for a user (with projects) or a group. The Projects page warns the user only of a quota near its limit (from 80 %, amber) or full (red, "nothing new can be launched"); it shows no other usage line (the user found them noisy).

## Scratch per machine

Settings → Jobs → Node capabilities shows each machine's scratch (`pages/Settings/NodeScratch`): none, its folder with free space, or why it cannot be used (as that machine reports it), and for `settings.manage` a "Change" dialog (`saveNodeScratch`; empty removes it; the machine's protocol worker must be restarted). Under it, what the last cleaning did (folders removed, space freed, errors) and, for `jobs.manage`, "Clean now" (`cleanNodeScratch`; the list reloads a few seconds later).
